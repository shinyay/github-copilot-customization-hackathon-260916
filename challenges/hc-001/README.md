# HC-001 根拠を示せるJavaチームメイトを育てよう

**言語:** **日本語** / [English](../../en/challenges/hc-001/README.md)

## シナリオ

Java コードの調査や変更を Copilot に依頼すると、もっともらしい説明が返ってきても、実際にどのファイルを読み、何を実行し、どこから推測したのかが分からないことがあります。

このシナリオでは、毎回同じ注意をプロンプトに加える代わりに、リポジトリ全体で守る「根拠に基づく進め方」を Repository Instructions として設計します。題材は、`Money.tax` に不正な丸め方法を指定した場合の処理です。本番コードの挙動と既存のテストを維持したまま、境界値のテストを追加する依頼で試します。

## この機能とは

Repository Instructions は、リポジトリ内の作業で Copilot に継続的に伝えたい規則を、Markdown ファイルに記述する仕組みです。GitHub Copilot が対応している環境では、通常 `.github/copilot-instructions.md` を使います。

ここで指定するのはコードの答えではなく、ほかの作業にも再利用できる進め方です。

- 指定されたソースとテストを先に読む
- 事実・推論・未確認を分ける
- 重要な主張をファイルとシンボルに結び付ける
- 実行環境があれば、対象を絞ってコンパイルやテストを実行する
- 実行していない検証を成功と書かない

Instructions は、テスト、レビュー、人による判断の代わりにはなりません。反映のされ方や出力は、クライアント、モデル、利用できるツールによって異なります。最終的には、ソースとターミナルの実行結果を人が確認します。

## 向いていること / 向いていないこと

**向いていること**

- 多くの Java 調査で繰り返す品質ルール
- リポジトリ全体で共通にしたい根拠の示し方
- 「実行したこと／していないこと」を明確にする習慣

**向いていないこと**

- 一度だけ使う長い手順
- 特定のバグの正解やテストコードを記憶させること
- シークレット、個人名、環境固有の URL の保存
- 単体テスト、レビュー、承認、アクセス制御の代替

## ゴール

1. Java 作業へ再利用できる短い Repository Instructions を作る。
2. 次の固定依頼に対して、ソースとテストの根拠、実行結果、未確認事項が分かる回答を得る。
3. `validation.rounding` による入力検証と、金額計算に使う丸めモードを混同していないか確認する。

固定依頼:

> `Money.tax` の `UNKNOWN` / invalid rounding 境界について、production code と既存 expectation を保った test を `CommonRulesTest.java` に追加してください。`validation.rounding` と金額計算の rounding を区別し、根拠、実行結果、未確認事項を報告してください。

## 用意するもの

- Repository Instructions に対応した GitHub Copilot 環境
- 変更してよい Java リポジトリの作業用ブランチまたはワークツリー
- 次の対象ファイル
  - `wholesale-core/src/main/java/jp/co/tsubame/wholesale/common/Money.java`
  - `wholesale-core/src/test/java/jp/co/tsubame/wholesale/common/CommonRulesTest.java`
- テストを実行する場合は、そのリポジトリが指定する Java/JDK とビルドツール

このディレクトリの `starter\` には、次の無効な状態の素材があります。

- [Repository Instructions の編集例](starter/customization/copilot-instructions.md.template)
- [Money.java の固定抜粋](starter/reference/Money.java.excerpt.md.template)
- [CommonRulesTest.java の固定抜粋](starter/reference/CommonRulesTest.java.excerpt.md.template)
- [任意比較メモ](starter/worksheet/comparison.md.template)

すべて `.template` のままなので、このリポジトリでは有効なカスタマイズになりません。

## 準備

1. まず [リポジトリ全体の始め方](../../README.md#始め方) を確認します。
2. 対象リポジトリの `Money.java` と `CommonRulesTest.java` を読みます。対象リポジトリを用意できない場合は、`starter\reference\` の固定抜粋を使って、静的な設計を練習できます。
3. 回答を見る前に、確認したい行動を 2〜4 個決めます。例:
   - ソースやテストの引用が主張を支えている
   - 事実と推論が分かれている
   - 実行したコマンドと結果が書かれている
   - 実行できない場合に未確認を残している
4. `starter\customization\copilot-instructions.md.template` を読み、対象リポジトリに必要な規則だけを選びます。チャレンジ側の `.template` はそのまま残し、対象リポジトリにだけ `.github/copilot-instructions.md` として配置します。
5. 特定のテストの答え、例外アサーションの形式、この演習でしか使わないファイル名は Instructions に埋め込まないでください。

## 試してみる

1. 対象リポジトリを GitHub Copilot で開き、新しい会話を開始します。
2. 上の固定依頼をそのまま送ります。
3. Copilot が提案または編集した差分を確認します。
4. 次の点をソースと照合します。
   - `Money.tax` が受け付ける丸め指定と、不正値で進む分岐
   - 既存のテストが保護している、有効な丸め方法の境界
   - 本番コードを変えず、境界値のテストだけを追加しているか
   - `validation.rounding` と計算結果の丸めを別の論点として説明しているか
5. 対象リポジトリに公式のテスト手順があり、実行環境も利用できる場合に限り、最小限の関連テストを実行します。Copilot の自己申告に頼らず、ターミナルで実行したコマンド、終了結果、失敗内容を自分で確認します。

## 任意: 比較する

効果を確認したい場合は、手動で簡単に確認します。

1. Instructions を置かない状態で固定依頼を一度試す（Baseline）。
2. 同じソース、依頼、モデル、ツールの条件を保ち、新しい会話で Instructions を有効にして試す（Customized）。
3. [比較メモ](starter/worksheet/comparison.md.template) に、引用、事実／推論／未確認、テストの扱い、回答の長さ、不要な作業を記録する。

まったく同じ条件を再現できない場合は、優劣を断定せず、条件の違いを明記します。差がない、回答が長くなった、余計なコマンドが増えたという結果も有用です。

## 確認ポイント

- Instructions は今回の正解ではなく、別の Java 作業にも使える規則か
- 重要な主張に、ファイルとシンボルの根拠があるか
- コードの読解と実行による確認を分けているか
- 実行していないテストを成功したと表現していないか
- 既存の期待結果と本番コードの挙動を不用意に変えていないか
- 不正な入力の検証と、金額計算の丸めを区別しているか

## 発展

- 同じ Instructions を別の小規模な Java 調査に使い、引用が多すぎたり回答が長くなりすぎたりしないか確かめる
- 規則を一つ削り、失われる品質と保守しやすさを比べる
- テストを実行できる作業と静的読解だけの作業で、報告形式をどう変えるか考える

## 制約・代替手段・安全

- Repository Instructions を利用できない場合は、選んだ本文を依頼の前に手動で貼り付けられます。これは手動の代替手段であり、自動検出を確認したことにはなりません。
- Java を実行できない場合は、コンパイルとテストが未実行であることを明記し、ソースとテストから確認できる範囲だけを報告します。
- 固定抜粋は設計練習用です。対象リポジトリを利用できる場合は、実際のファイルを正とします。
- 未承認のソフトウェアの導入、権限の回避、シークレットや非公開データの貼り付けは行いません。
- Copilot の提案は必ず差分とテストでレビューし、実際の金額や業務判断にそのまま適用しません。
