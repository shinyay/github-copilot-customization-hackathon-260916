# HC-003 ディレクトリごとの規則をAGENTS.mdで伝えよう

**言語:** **日本語** / [English](../../en/challenges/hc-003/README.md)

## シナリオ

受注承認の説明を Copilot に依頼すると、サービスの入口だけで結論を出す回答もあれば、継承元の共通処理や委譲先まで追う回答もあります。チームは、「どの調査にも必要な短い規則」と「特定のディレクトリでだけ必要な観点」を整理したいと考えています。

このシナリオの本編では、対象リポジトリのルートに配置する `AGENTS.md` を一つだけ設計します。ディレクトリ固有の案は設計メモに残しますが、nested AGENTS や親リポジトリからの検出は本編に含めません。

## この機能とは

`AGENTS.md` は、対応するコーディングエージェントに、リポジトリでの作業規則を伝える Markdown の指示文書です。ワークスペースルートの `AGENTS.md` には、たとえば次のようなチーム共通の習慣を記述できます。

- 入口のメソッドだけでなく、共通処理と委譲先まで読む
- 認証・認可と業務条件を分ける
- 重要な主張をファイルとシンボルに結び付ける
- 事実、推論、未確認を区別する

`AGENTS.md` は、`.agent.md` のロール定義ではありません。新しいエージェントの選択肢、ツール、実行権限、Java の動作を作るものではなく、自然言語で記述する指示です。ファイルを保存したこと、クライアントが検出したこと、本文が実際に使われたこと、回答が改善したことは、それぞれ分けて確認します。

複数のディレクトリに置く nested AGENTS は、Experimental 機能として扱われます。親リポジトリからカスタマイズを検出する機能にも、別の条件があります。複数文書の厳密な継承順や「常に子が優先される」といった規則を、パスだけから仮定しません。本編ではルートの一つだけを使います。

参考: [VS Code Custom instructions](https://code.visualstudio.com/docs/agent-customization/custom-instructions)

## 向いていること / 向いていないこと

**向いていること**

- 多くの調査で繰り返す短い作業規則
- 対応する複数のコーディングエージェントと共有したいリポジトリの習慣
- 根拠、未確認事項、実行していないことの報告方法

**向いていないこと**

- 一度だけの長い依頼
- 特定のロール一覧や受注承認の正解
- アクセス制御、実行許可、モデルやツールの設定
- テストや人によるソースレビューの代替

固定依頼だけで十分なら、`AGENTS.md` を追加しない判断にも価値があります。

## ゴール

1. ルートに常設する規則と、ディレクトリ固有の規則を分ける。
2. ルートの `AGENTS.md` の本文を、再利用できる短い規則に絞る。
3. `OrderService.approve` から共有の `require` とその委譲先まで、根拠付きで読めるか確かめる。
4. 認証・認可の条件と、受注の業務条件を混同しない。
5. 指示による効果だけでなく、回答が長くなりすぎないか、保守の負担が増えないかも確認する。

## 用意するもの

- ルートの `AGENTS.md` に対応する GitHub Copilot / コーディングエージェント環境
- 変更してよい対象リポジトリのブランチまたはワークツリー
- 次のファイルを含む対象リポジトリ

| 読む入口 | 確認すること |
| --- | --- |
| `wholesale-core/src/main/java/jp/co/tsubame/wholesale/service/OrderService.java` | `approve` の入口、呼び出すガード、その後の条件 |
| `wholesale-core/src/main/java/jp/co/tsubame/wholesale/service/BaseService.java` | 継承元の `require` と委譲先 |
| `wholesale-core/src/main/java/jp/co/tsubame/wholesale/common/Actor.java` | `require` から使われるロール判定 |

`starter\` には次の無効な状態の素材があります。

- [固定依頼](starter/request.txt.template)
- [ルートの AGENTS.md の編集例](starter/customization/AGENTS.md.template)
- [設計と任意比較のワークシート](starter/worksheet/comparison.md.template)

すべて `.template` のままなので、このチャレンジディレクトリでは有効なカスタマイズになりません。

## 準備

1. [リポジトリ全体の始め方](../../README.md#始め方) を確認します。
2. 回答を見る前に、観察する項目を 2〜3 個に絞ります。例:
   - 共有処理と委譲先まで追ったか
   - 引用先が主張を支えているか
   - 認証・認可と業務条件を分けたか
   - 未確認事項を残したか
3. [ワークシート](starter/worksheet/comparison.md.template) に、ルートへ置く共通規則の候補と、ディレクトリ固有のため今回は置かない候補を書き分けます。
4. [AGENTS.md.template](starter/customization/AGENTS.md.template) を編集の出発点とし、この演習でしか使わない答え、ロールの対応表、環境固有の情報を除きます。チャレンジ側は `.template` のまま残します。
5. 実際に試すときだけ、選んだ本文を対象リポジトリのルートに `AGENTS.md` としてコピーします。既存の `AGENTS.md` がある場合は上書きせず、内容と所有者を確認して作業を止めます。
6. 本編では、nested AGENTS、親リポジトリのカスタマイズ、別形式の Instructions、設定変更を追加しません。

## 試してみる

1. 対象リポジトリのルートを、ワークスペースルートとして開きます。
2. 新しい会話を開始し、[request.txt.template](starter/request.txt.template) の全文をそのまま送ります。
3. Copilot が必要なファイルを読み取れるようにしますが、`starter\` の原稿や比較メモを業務ロジックの根拠として渡しません。
4. 回答を次の順でソースと照合します。
   - `OrderService.approve` 内の呼出し
   - `BaseService.require` の定義
   - `require` が委譲する `Actor` の判定
   - null や早期 return の分岐
   - 認証・認可を通る条件と、受注の業務条件
5. 保存したパス、クライアントが示した検出、本文利用を確認できる表示、最終回答を分けて記録します。よい回答が得られたことだけを根拠に、本文が自動的に使われたとは推定しません。

この本編では、ソースを静的に読み取ります。Java のテスト、データベース、Web、バッチは起動せず、ソース、テスト、設定も変更しません。

## 任意: 比較する

比較する場合は、二つの新しい会話で短く行います。

1. 対象リポジトリにルートの `AGENTS.md` がない状態で固定依頼を試す（Baseline）。
2. 選んだ本文を記述したルートの `AGENTS.md` だけを追加し、同じ固定依頼を試す（Customized）。
3. ソース、モデル、ツール、参照方法をそろえ、[ワークシート](starter/worksheet/comparison.md.template) に差を残します。

本文を設計するために使った試行は比較に流用しません。条件がそろわない場合、ほかの指示が混ざる場合、検出を観測できない場合は、機能の効果を断定しません。

## 確認ポイント

- ルートに置いた規則は、別の調査にも使えるか
- ディレクトリ固有の観点をルートに詰め込みすぎていないか
- `AGENTS.md` をロール定義や権限設定として説明していないか
- メソッド内のロール文字列だけで結論を出さず、共通処理まで追ったか
- 認証・認可と受注の業務条件を分けたか
- 事実、推論、未確認事項を、ファイルとシンボルを添えて示したか
- 指示の保存、検出、本文利用、回答を区別したか
- 読み落としだけでなく、長文化や保守の負担も確認したか

## 制約・代替手段・安全

- ルートの `AGENTS.md` が使われたことを確認できない場合は、同じ本文を固定依頼の前に手動で貼り付けられます。これは手動の代替手段であり、ルートからの検出を確認したことにはなりません。
- クライアントに検出や参照の表示がない場合は、本文が使われたかどうかを未確認のままにします。
- 実在する利用者や受注の承認可否を判断せず、実データ、認証情報、シークレットを使いません。
- データベース、Web、バッチ、Java のテストは起動せず、実行していない検証を成功したと書きません。
- 既存の `AGENTS.md`、User/organization 設定、Memory、他人のカスタマイズを削除または退避して条件を作りません。
- nested/parent 機能を本編に含めません。試す場合は、補足ガイドに従って別の使い捨て環境で行います。
